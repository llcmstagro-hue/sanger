# Progressive Reveal

Humans read the first three lines, skim the middle, and open attachments only if the opening earned it. Structure every substantial deliverable so each layer answers "should I keep going?" before asking for more attention.

## The reveal ladder

Deliver in this order, stopping at the depth the request warrants:

1. **Takeaway** — one or two sentences: the answer, the decision, the number. Written so a reader who stops here still gets the outcome.
2. **Summary** — 3–6 bullets: the key findings or the shape of what was built, each independently useful.
3. **Visual** — the one chart, mockup, table, or diagram that makes the summary concrete.
4. **Data / detail** — the supporting tables, code paths, or per-item breakdown, in collapsible or clearly skippable sections.
5. **Appendix** — methodology, raw material, edge cases, full listings. In a file, never inline.

Never invert the ladder. "I looked at 14 files, first in file A…" is an appendix wearing the takeaway's clothes.

## Writing the takeaway

- State the conclusion, not the activity: "The March close date is at risk — two contingencies are unresolved" beats "I reviewed the timeline."
- Include the single most decision-relevant number.
- If the news is bad or the answer is "no", say so in the takeaway — don't make the reader excavate for it.
- No throat-clearing ("Great question!", "I've completed the analysis you requested").

## Chunking long deliverables

- One idea per section; scannable headers that state the point ("Comps support $865k–$890k"), not the topic ("Comps").
- Hard cap inline tables at ~10 rows; longer tables go to a file or appendix with the top rows inlined.
- For multi-part work, deliver part 1 fully rather than all parts sketchily, and name what's queued: "Next: buyer deck (waiting on your OK for this structure)."
- When a message would exceed a screen or two, split it: send the ladder's top three rungs, offer the rest.

## Files vs inline text

Send as a **file / artifact** when:
- The content is a deliverable the user will reuse, forward, or open later (decks, mockups, reports, datasets).
- It exceeds ~60 lines or needs formatting that chat mangles (wide tables, side-by-side comparisons).
- It's visual or interactive — HTML artifacts for anything rendered.

Keep **inline** when:
- The user needs it in the next 10 seconds to make a decision (the recommendation, the three options, the one number).
- It's a snippet they'll copy directly (a command, a paragraph of listing copy).
- Asking them to open a file would cost more than reading five lines.

Rule of thumb: decisions inline, deliverables as files — and every file gets a one-line inline description of what's inside and why they'd open it.

## Multimodal ordering

When mixing text, images, and files in one delivery:

- Text takeaway first, always — a bare artifact link with no framing forces the user to do the summarizing.
- One primary visual per message; additional visuals go in the artifact/appendix.
- Caption every visual with its takeaway ("Option B fits the mobile grid best"), since visuals get forwarded without their surrounding text.
- Don't duplicate: if the chart is in the artifact, inline the conclusion it shows, not a second copy of the chart.

## Calibrating depth

- Quick factual question → rung 1 only. Do not ceremonially build a ladder for a one-line answer.
- "Look into X" → rungs 1–3, offer 4.
- Formal deliverable → all five rungs, with 4–5 in the artifact.
- When the user says "just give me everything", still lead with the takeaway — then give everything.

## Checklist

- [ ] First sentence contains the answer or outcome
- [ ] Summary bullets survive being read alone
- [ ] Exactly one primary visual, captioned with its takeaway
- [ ] Long detail in skippable sections or a file, never mid-message walls
- [ ] Each file introduced with one line saying what it is and why to open it
- [ ] Depth matches the ask — no ladder for one-liners, no one-liner for deliverables
